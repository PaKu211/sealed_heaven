# Sealed Heaven — Independent G0 Architecture Review

**Verdict — FAIL.** Four documentation blockers leave observable outcomes or milestone boundaries undefined. The design can support a pure Rust, Bevy-free C0.1 once those blockers are closed and the revised baseline is approved. G0 is a specification gate. The findings below are based on document review and upstream source verification. No implementation, build, benchmark, asset generation, or dataset import was performed.

## Proposed C0.1 implementation

**Feasible as a single pure Rust crate.** Use `sealed_sim` and in-package tests that drive an integer clock, immutable tick batches, a serial commit, named RNG streams, a small ordered event stream and a canonical checksum. Two authored actor IDs and one synthetic exclusive slot are sufficient to test conflicts. The slot is a fixture state transition. The production reservation API, persistence DTOs, Bevy types and asset/JSON loaders belong to their later milestones. This fixture establishes reusable rules for determinism while leaving the eventual game schema open.

### Proposed fixture contract

- Tick 0 is the initial checkpoint. One explicit step closes/applies the next tick's admitted batch and advances one tick, including on an empty batch. A paused host invokes zero steps. Each replay input identifies its submission boundary so pre-queued pending work reconstructs identically. Commands submitted at a boundary may target any strictly future tick. All submissions for a boundary form one closed batch.
- Sort due commands by `(target_tick, actor_id, producer_id, sequence)` for the single C0.1 commit phase. Actor and producer IDs and sequence are numeric with stable ascending order. The sort tuple is also the command identity in C0.1. Exact duplicate records collapse to one while queued or within the admission batch. If one identity is reused with a different payload, fail the admission batch atomically with a stable diagnostic and leave queued state untouched. Commands for closed ticks are deterministic ingress failures with no mutation. Ingress failures are diagnostics; gameplay rejections from due admitted commands are ordered domain events. A successful commit mutates only the slot and appends one event. When eligibility fails, append one typed rejection and leave the slot unchanged. Issue event IDs in commit order. For the proposed oracle, submit claims by actor 2 and actor 1 for the same vacant slot, both for tick 2 with producer 1 and sequence 0. Tick 1 leaves the slot vacant and emits no event. Tick 2 awards it to actor 1 and emits a successful claim followed by an occupied-slot rejection of actor 2. Reversing the input records gives the same result.
- Use a revisioned field list and fixed-width unsigned little-endian encoding for the fixture. Encode lengths and discriminants explicitly, IDs in sorted order for state collections and events in emission order. Define checksum input as a domain-tagged state record plus consequential event cursor and digest. Report the event stream separately. Include logical tick, fixture/content identity, seed, authoritative slot/actor fixture state, queued inputs and RNG ordinals. Update the event digest when emitting a consequential event, using SHA-256 over a versioned event tag, the previous digest and the encoded event. Specify field positions, widths, tag values and the initial digest in the R2 fixture. Keep output hashes at explicit checkpoints.
- For a random decision, derive a 32-byte seed via SHA-256 over a fixed version tag, a fixed numeric subsystem tag, world seed, subject ID and decision ordinal encoded unambiguously. Use `ChaCha12Rng::from_seed` and raw integer output for the vector/path actually exercised in C0.1. The next decision ordinal is scoped per subsystem and subject. Test that extra draws within one decision leave another named stream unchanged. This proposal has no generalized distribution API requirement.
